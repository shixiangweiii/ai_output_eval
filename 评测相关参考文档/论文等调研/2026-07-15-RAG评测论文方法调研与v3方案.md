# RAG 评测论文方法调研与 v3 方案

> 日期：2026-07-15  
> 调研目标：寻找能直接改善本仓库“试卷、打分规则、评测脚本”的方法，而不是简单罗列框架。  
> 结论：继续沿用考试题库很合理，但应从“长片段逐字包含”升级为“原子信息覆盖 + 标准排名 qrels + 模块化端到端评测 + 统计置信度”。

## 1. 方法谱系

| 方法/论文 | 核心做法 | 对本项目最直接的启发 |
| --- | --- | --- |
| [BEIR, NeurIPS Datasets and Benchmarks 2021](https://datasets-benchmarks-proceedings.neurips.cc/paper/2021/hash/65b9eea6e1cc6bb9f0cd2a47751a186f-Abstract-round2.html) | 用异质任务和领域评测零样本 IR，强调跨分布泛化 | 不能只在 10 篇同源合成文档上排名；需要多领域、规模梯度和独立盲测 |
| [TREC relevance judgments / pooling](https://trec.nist.gov/data/reljudge_eng.html) | 多系统结果池化后形成 qrels，再用标准工具评测 | 汇总 aRAG/Dify/GraphRAG 的候选池，人工或半自动补齐分级相关性，避免只按单一 GT 片段判断 |
| [TREC 2025 RAG Retrieval](https://trec.nist.gov/pubs/trec34/appendices/trec2025-rag-retrieval.html) | 官方检索榜同时报告 nDCG@30、nDCG@100、Recall@100 | 当前只报 Recall/MRR 不足；应加入 nDCG 和不同深度/预算曲线 |
| [RAGChecker, NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/hash/27245589131d17368cccdfa990cbf16e-Abstract-Datasets_and_Benchmarks_Track.html) | 把 GT/回答分解为 claim；检索器评 claim recall 与 chunk-level context precision，生成器评利用率、噪声敏感、幻觉等 | 把长 snippet 拆成原子 claim，可显著降低分块边界偏差；检索与生成分开诊断 |
| [EXAM Answerability, 2024](https://arxiv.org/abs/2402.00309) | passage 若能回答题库中的关键小问题就相关；EXAM Cover 强调信息覆盖且不奖励重复，EXAM Qrels 可接 trec_eval | 本仓库本来就是“考试”，可把每个复杂题拆成信息点小题；覆盖度天然抑制重复块 |
| [TREC 2024 RAG Evaluation](https://trec-rag.github.io/annoucements/evaluation/) | 先建相关段与信息 nuggets，再分别评答案支持度、流畅性和 nugget 覆盖；自动标注后人工修订 | 未来生成评测应按原子信息完整性和逐句引用支持评分，而不是只做答案字符串相似度 |
| [AutoNuggetizer, 2024](https://arxiv.org/abs/2411.09607) | 信息 nugget 在语义层面匹配，可标 vital/okay；自动生成/分配并与人工版比较 | `required_claims` 可带重要性；自动 judge 只能作为可审计的第二层，不应隐藏 exact 结果 |
| [RAGAS, EACL 2024](https://aclanthology.org/2024.eacl-demo.16/) | 参考无关地评 faithfulness、answer relevance、context relevance | 没有人工 GT 时可做快速开发诊断；不适合取代当前确定性金标，应抽样校准 judge |
| [ARES, NAACL 2024](https://aclanthology.org/2024.naacl-long.20/) | 评 context relevance、answer faithfulness、answer relevance；用少量人工标注和 PPI 生成置信区间 | 引入 LLM judge 时必须有域内人工验证集、误差修正和置信区间，而不是只报 judge 平均分 |
| [MultiHop-RAG, COLM 2024](https://arxiv.org/abs/2401.15391) | 为推断、比较、时序、Null 四类多跳题提供多证据 GT；检索报 MAP/MRR/Hit | 当前题型方向正确，但需要 Null 真无答案题、MAP/nDCG，以及“整链到齐”指标 |
| [RGB, AAAI 2024](https://ojs.aaai.org/index.php/AAAI/article/download/29728/31250) | 分开测噪声鲁棒、负向拒答、信息整合、反事实鲁棒 | 对抗题不应混成一个标签；应按噪声、无答案、冲突、反事实分别建集与计分 |
| [UAEval4RAG, 2024](https://arxiv.org/abs/2412.12300) | 将不可回答分成信息不足、错误前提、无意义、模态受限、安全、库外六类，并同时报告拒答和可接受度 | 当前 schema 无法表达空 GT；未来需要 `answerability` 与拒答/澄清分类，且与答案正确率共同看 |
| [BRIGHT, ICLR 2025](https://openreview.net/forum?id=ykuc5q381b) | 1398 个真实、推理密集型检索 query；主要用 nDCG@10，展示显式 query reasoning 对检索的提升 | 最新卷的低词面重合方向有价值，但要增加自然真实 query 和盲测，避免只用人为设计题 |
| [KILT, NAACL 2021](https://aclanthology.org/2021.naacl-main.200/) | 在统一知识快照上同时评下游任务与 provenance | 固定 corpus snapshot，并把检索来源和最终答案两条链同时纳入端到端评测 |

## 2. 对当前方法的判断

### 2.1 应保留的部分

- 保留检索-only 评测器。模块化定位问题比只看最终答案更可靠。
- 保留 `source_document + evidence`，但把 evidence 拆得更原子并使用稳定 ID。
- 保留 exact match。它可重复、便宜、可解释，适合作为高精度信号和语料入库一致性检查。
- 保留逐题详细诊断、完整链、文档覆盖、图片来源与排序异常。
- 保留普通请求失败计零和鉴权中止不出有效总分的原则。

### 2.2 不应继续作为唯一主口径的部分

- 一个长 snippet 必须完整包含在一个 chunk。
- 所有题只用一个 Query-macro Recall 分数排名。
- 固定 chunk K 跨不同分块方案比较。
- 把所有非 GT chunk 一律视为同等不相关，不区分普通噪声和误导性 hard negative。
- 用图片 URL 文本出现代替真实多模态召回。
- 用检索证据分数声称系统具备拒答、推理、答案正确性或工具调用能力。

## 3. 推荐的评测架构

```text
Corpus Snapshot + Ingestion Manifest
                 │
                 ├── Retrieval-only
                 │     ├── exact claim match
                 │     ├── semantic/entailment claim match
                 │     ├── qrels ranking metrics
                 │     └── cost/latency/budget metrics
                 │
                 ├── Oracle-context Generation
                 │     └── 隔离生成器能力
                 │
                 ├── Retrieved-context End-to-end
                 │     └── 真实 RAG 效果
                 │
                 └── No-context Baseline
                       └── 区分模型自有知识与 RAG 增益
```

这样能回答四种不同问题：

1. 检索器有没有找到所需信息？
2. 给了完美证据，生成器会不会用？
3. 真实组合后答案是否正确、完整、可引用？
4. RAG 相比模型裸答到底带来多少增益或噪声？

## 4. v3 考卷 schema 建议

### 4.1 考卷级元数据

```json
{
  "schema_version": "3.0",
  "suite_id": "retrieval-regression-2026q3",
  "split": "dev|regression|blind_test",
  "purpose": "retrieval_only|generation|end_to_end",
  "corpus_snapshot": {
    "snapshot_id": "corpus-20260715-a",
    "manifest_sha256": "...",
    "document_count": 1000,
    "ingestion_profile_id": "plain-500t-overlap50"
  },
  "authoring_provenance": {
    "source": "real_query|expert|synthetic",
    "review_status": "single|double|adjudicated",
    "exposed_to_system_tuning": false
  }
}
```

### 4.2 题目级核心字段

```json
{
  "id": "q_001",
  "question": "...",
  "answerability": "answerable|unanswerable|needs_clarification|needs_tool",
  "capability_tags": ["multi_hop", "temporal", "hard_negative"],
  "difficulty_features": {
    "required_docs": 3,
    "required_claims": 4,
    "reasoning_hops": 3,
    "lexical_overlap_band": "low",
    "modality": "text"
  },
  "required_claims": [
    {
      "claim_id": "q_001_c1",
      "text": "...",
      "importance": "vital",
      "source_document_id": "doc_01",
      "source_span_sha256": "...",
      "acceptable_spans": ["逐字证据 A", "等价逐字证据 B"]
    }
  ],
  "qrels": [
    {"document_id": "doc_01", "chunk_or_span_id": "span_123", "relevance": 3}
  ],
  "hard_negatives": [
    {"document_id": "doc_09", "span_id": "span_888", "reason": "旧版本冲突"}
  ],
  "reference_answer": "...",
  "citation_requirements": ["q_001_c1"]
}
```

设计要点：

- `difficulty` 不再只是主观标签，而由可观察特征支持；标签可根据基线通过率后校准。
- `required_claims` 是原子信息单元，避免一条长 snippet 被分块边界截断。
- exact match 可以检查 `acceptable_spans`；semantic judge 检查 claim 是否被 chunk 蕴含，两者都保留。
- `qrels.relevance` 支持 nDCG；例如 3=直接完整证据、2=部分/间接证据、1=背景相关、0=不相关。
- `hard_negatives` 单独计算误导召回，不与普通噪声混为一谈。
- 真正不可回答题允许 `required_claims=[]`，评分目标转为拒检、澄清或拒答。

## 5. 指标面板建议

### 5.1 检索覆盖

- `query_macro_claim_recall@k`：每题 claim recall 等权，保持当前主分的业务直觉。
- `claim_micro_recall@k`：所有 claim 汇总，反映总体信息点覆盖。
- `complete_chain_rate@k`：所有 vital claim 全部到齐的题占比；多跳业务必须重点看。
- `document_recall@k`：找对来源文档的能力。
- `min_k_for_full_chain`：凑齐一题所有证据所需最小 K；没凑齐为无穷。

### 5.2 排名与噪声

- `nDCG@k`：支持分级相关性和位置折损，适合作为主排名指标之一。
- `MAP@k`：多相关项检索比只看第一条的 MRR 更完整。
- `MRR@k`：保留，用来描述第一条有效证据来得多快，但不代表链完整。
- `context_precision@k`：含至少一个 GT claim 的块占比，对齐 RAGChecker。
- `hard_negative_rate@k`：误导性证据进入 Top-K 的比例。
- `duplicate_source_rate@k`、`unique_source_count@k`：诊断同文档挤占。

### 5.3 预算与稳定性

- `claim_recall@token_budget`：例如 1k/2k/4k 输入 token，公平比较父子与普通分块。
- 每题 `retrieval_latency_ms`、p50/p95、重试次数、返回 token/字符数。
- 质量-成本 Pareto 前沿，不只比较一个 K。
- 同配置多次运行的均值、标准差、Top-K 集合 Jaccard 和排名相关。

### 5.4 生成与端到端

- Answer claim precision/recall/F1：正确、完整。
- Faithfulness：回答 claim 是否被所给上下文支持。
- Context utilization：已检索到的必要 claim 有多少被答案真正使用。
- Citation precision/recall：逐句引用是否支持、关键 claim 是否有引用。
- Unanswerable/clarification/tool-call 分类准确率和 acceptable rate。
- Counterfactual/noise sensitivity：是否被错误或冲突检索结果带偏。

## 6. exact 与 LLM judge 的组合方式

建议采用三态而不是用 LLM judge 覆盖 exact：

```text
exact_hit      = 文档 ID 正确且允许证据 span 归一化包含
semantic_hit   = exact 未命中，但 claim 被返回内容蕴含
miss           = 两者均未命中
```

报告同时给：

- Strict Exact Claim Recall：最可复现，便于发现入库/切分漂移。
- Semantic Claim Recall：更接近“信息是否可用”，降低分块和措辞偏差。
- Disagreement Queue：exact 与 semantic 不一致的样本，供人工复核和 judge 校准。

引入 LLM judge 时的最低要求：

1. 固定 judge 模型版本、prompt、温度和输出 schema。
2. 至少准备域内人工验证集；ARES 的做法说明 judge 平均分本身不足以表达误差。
3. 报告 judge-human agreement、置信区间和失败样例。
4. 防止同一模型既生成题目/答案又担任唯一 judge。
5. 对高风险题保留人工仲裁；自动结果不能覆盖原始 evidence 与判定理由。

## 7. 不建议直接设计任意加权总分

当前参考文档曾提出 Retrieval/Ranking/Generation/Citation/Multimodal 按固定比例相加。这种分数便于汇报，但权重若没有业务数据支持，会制造虚假的精确性。

优先方案是“指标面板 + 发布门槛”：

```text
Retrieval macro claim recall@5 >= 0.80
Complete chain rate@5 >= 0.60
nDCG@5 >= 0.70
Hard-negative rate@5 <= 0.05
End-to-end answer claim F1 >= 0.80
Citation support precision >= 0.95
Unanswerable acceptable rate >= 0.90
p95 latency <= 目标值
```

如果管理上必须有一个总分，权重应根据真实用户满意度、任务成功或人工偏好拟合，并通过留出集验证，而不是先拍脑袋定 40/40/20 或 30/20/30/10/10。

## 8. 统计比较协议

### 8.1 同卷配对比较

- 对每题差值做 paired bootstrap 95% CI。
- 对均值差可做配对随机化/permutation test。
- 多系统两两比较时做 Holm 等多重比较校正。
- 同时报告效应量和 Win/Tie/Loss，不只报 p 值。

现有 25 题示例已经说明必要性：aRAG 比 GraphRAG 高 8 分，但配对区间跨 0，不能据此下“稳定更强”的结论。

### 8.2 样本与切片

以下只是工程起始目标，不是论文规定的固定门槛：

- Dev：50～100 题，快速定位失败。
- Regression：100～200 题，冻结并持续运行。
- Blind acceptance：200+ 题，尽量来自真实 query；每个核心业务切片至少约 30 题再单独解释均值。
- 长尾/安全/高风险切片可采用过采样，但总览同时报告按真实流量分布重加权的成绩。

对重复运行有随机性的检索器，每配置至少跑 3 次；若方差明显，再增加重复次数。

## 9. 试卷治理建议

### 9.1 三套数据角色

| 数据集 | 是否允许看答案/失败 | 用途 |
| --- | --- | --- |
| Dev | 允许 | 调 prompt、切分、召回与重排；最新全困难卷可归入此类 |
| Regression | 可看但冻结 | 发布前防止已知问题回归 |
| Blind Test | 不向调参人员公开 GT | 做版本验收和系统排名，定期轮换 |

### 9.2 真实分布与压力分布分开报告

- `production-weighted`：按线上真实 query 类型分布，代表用户体验。
- `stress/adversarial`：多跳、无答案、冲突、多模态、低重合，代表能力上限和安全边界。
- 不要把全困难压力卷的分数直接当线上总体质量。

### 9.3 语料版本控制

每次试卷必须绑定：

- 文档稳定 ID、文件 hash、整体 manifest hash。
- 解析器版本、chunking 配置、embedding/reranker、GraphRAG 图构建版本。
- 每个 backend 的 dataset alias/id 与入库完成时间。
- 任何语料改动后，旧 snapshot 不覆盖；新建 snapshot 并重新入库所有参评后端。

## 11. 落地路线图

### Phase 0：一两天内完成的可信度修复

- 修正 macro/micro 名称。
- 请求侧 K 与评分 K 对齐。
- 增加 run manifest、语料/考卷 hash、时延与返回深度。
- validate-only 加 corpus-aware 模式。
- 更新旧帮助文案与结果路径。

### Phase 1：metrics v2.1

- 输出 macro、micro、complete-chain、K 曲线、聚合重复率。
- 报 paired bootstrap CI 和可比性警告。
- 增加离线 replay/rescore，减少重复调用线上接口。

### Phase 2：metrics v3.0 retrieval

- 迁移为原子 claims + stable IDs + qrels + hard negatives。
- exact/semantic 双层评分。
- nDCG/MAP、token budget、阈值与真无答案检索。
- 分离 Dev/Regression/Blind Test。

### Phase 3：generation / end-to-end

- 接入问答接口并做 oracle/retrieved/no-context 对照。
- claim F1、faithfulness、citation support、拒答、工具边界。
- LLM judge 人工校准与置信区间。

### Phase 4：线上闭环

- 脱敏采样真实 query、人工归因、线上反馈。
- 真实流量加权得分与压力集得分分开。
- 发布门槛、回归告警和失败样本队列。

## 12. 推荐优先阅读

1. [RAGChecker](https://proceedings.neurips.cc/paper_files/paper/2024/hash/27245589131d17368cccdfa990cbf16e-Abstract-Datasets_and_Benchmarks_Track.html)：最适合指导 claim-level 检索/生成诊断。
2. [EXAM Answerability](https://arxiv.org/abs/2402.00309)：与当前“考卷”范式最贴近，尤其是覆盖度与去重复思想。
3. [TREC 2024 RAG Evaluation](https://trec-rag.github.io/annoucements/evaluation/)：端到端 nugget、引用支持与人工修订流程。
4. [MultiHop-RAG](https://arxiv.org/abs/2401.15391)：多证据、推断/比较/时序/Null 题型设计。
5. [ARES](https://aclanthology.org/2024.naacl-long.20/)：LLM judge 的人工校准和置信区间。
6. [BRIGHT](https://openreview.net/forum?id=ykuc5q381b)：真实推理密集检索和低词面重合。

## 13. 本项目的一句话 v3 定义

> 在冻结语料、固定预算和可复现配置下，衡量系统是否以合理排序和成本召回回答每个 query 所需的全部原子信息，并进一步验证生成器是否完整、忠实、可引用地使用这些信息；所有排名同时给出不确定性和适用范围。
